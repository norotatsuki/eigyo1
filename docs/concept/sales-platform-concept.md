# 営業仕組み化プラットフォーム 構想書

- 版: 0.1 (初版・たたき台)
- 作成日: 2026-08-09
- 位置づけ: CCAGI Phase 1 (要件定義) の前段。ここで方向を決めてから `/generate-requirements` に渡す

---

## 1. 一言でいうと

**「日本の全法人を骨格とした企業データ基盤」を自前で持ち、そこから
「誰に・なぜ今・どの窓口で」を確定させて、メールと問い合わせフォームで
自動接触するまでを一本の流れにする。**

分解すると 4 つの部品になる。

| # | 部品 | 中身 | 難易度 |
|---|---|---|---|
| 1 | 法人マスタ | 日本の全法人の骨格 (法人番号・商号・所在地) | 低 (公的データが揃っている) |
| 2 | 企業プロフィール | 業種・規模・URL・技術・動き | 中 (収集と名寄せの設計次第) |
| 3 | 接触先の解像度 | 部署・役職・担当者・窓口 | **高 (ここが本丸)** |
| 4 | 接触の実行 | メール送信 / フォーム送信 / 反応の追跡 | 中 (到達性の作り込みが重い) |

多くの類似サービスは 1〜2 で止まっている。差がつくのは **3 の解像度** と、
**4 の到達性**。構想の重心もそこに置く。

## 2. 最初に押さえる法規制 — これが設計を規定する

技術より先にここを決める。**あとから直せない部分**だから。

### 2.1 メール送信 — 特定電子メール法 (特電法)

原則はオプトイン (事前同意) だが、**この事業を成立させる例外がある**。

> 法3条1項4号: 自己の電子メールアドレスを**公表している団体**、
> および営業を営む個人 (営業に関する内容に限る) は、事前同意なしに送信できる。
> ただし「営業メールを受け取らない旨を公表している」場合は除く。

つまり:

- 企業がサイトに載せている `info@` `contact@` 宛 → **同意なしで送信可能**
- サイトに「営業メールお断り」と書いてある → **送信禁止**。この文言の自動検出が必要
- 個人名付きアドレス (`yamada@`) → 法人の業務用なら 4 号の射程だが、
  名刺交換など接点の記録がある方が安全。**記録を残す設計にする**

送信時に必ず表示するもの (法4条):

1. 送信者の氏名または名称
2. **受信拒否の通知先** (URL またはメールアドレス)
3. 送信者の住所
4. 苦情・問い合わせの受付先

拒否された相手への再送は禁止 (法3条3項)。
→ **配信停止リストは絶対に送らない領域として、送信の直前に必ず照合する**。

罰則は措置命令 → 刑事罰。法人には重い罰金 (最大 3000 万円) が科される。
「知らなかった」では済まない領域。

### 2.2 担当者情報 — 個人情報保護法 (APPI)

**担当者の氏名 + 所属 = 個人情報**。公開情報から集めた場合も同じ。

- 取得時に**利用目的の公表が必要** (法21条)
  → プライバシーポリシーに「公開情報から営業目的で取得する」と明記する
- **第三者提供は原則として本人の同意が必要** (法27条)

ここが事業の形を分ける最大の分岐点:

| 進み方 | 意味 | APPI 上の負担 |
|---|---|---|
| **A. 自社利用型** | 自社 (または営業代行として) が送信するだけ。リストは外に出さない | 利用目的の公表で足りる。**軽い** |
| **B. リスト提供型** | 顧客にリストを渡す / 画面で見せてダウンロードさせる | 第三者提供に該当。**オプトアウト届出**を個人情報保護委員会に出し、公表・記録が必要。**重い** |

**推奨は A で始めて、B は後から足す。**
B は届出・公表・本人からの停止請求への対応体制がいる。
最初から背負うと、作る速度が落ちる。

### 2.3 問い合わせフォーム送信

- 特電法の「電子メール」の定義に**該当しない** → 特電法の規制の外
- ただし別のリスクが 2 つある:
  1. **サイト利用規約**で営業目的の送信を禁じている場合 → 規約違反
  2. **大量・反復送信** → 偽計業務妨害にあたるという指摘がある

自主基準として設計に組み込む:

- **1 社 1 回まで** (再送しない)
- 規約・フォーム近辺の「営業お断り」文言を検出したら**自動で除外**
- 送信間隔を空ける。同一時間帯に集中させない
- **CAPTCHA を検出したら送らない**。突破は絶対にしない
  (不正アクセス禁止法・業務妨害の領域に入る。ここは一線を引く)

### 2.4 情報収集 (クロール)

- 著作権法30条の4 により、情報解析目的の収集自体は適法性が高い
- ただし **robots.txt の尊重・レート制限は必須**。
  過去に図書館システムへの高頻度アクセスで逮捕に至った事例がある
  (2010年 岡崎市立中央図書館事件)
- 収集した生データをそのまま再配布するのは別問題。**加工して使う**

### 2.5 法規制から導かれる設計要件

| # | 要件 | 実装場所 |
|---|---|---|
| L1 | 配信停止リストとの照合を送信の直前に強制 | 送信ワーカーの直前フック |
| L2 | 「営業お断り」文言の検出と自動除外 | 収集時の判定 + 送信直前の再判定 |
| L3 | 全送信の記録 (宛先・日時・根拠・文面) を保存 | 監査ログ |
| L4 | CAPTCHA 検出でフォーム送信を停止 | フォーム送信ワーカー |
| L5 | robots.txt 遵守とドメイン別レート制限 | クローラ |
| L6 | 1 社 1 回のフォーム送信上限 | 送信の重複排除 |
| L7 | 本人からの開示・停止請求に応じる導線 | 管理画面 + 公開窓口 |

## 3. データ基盤 — 「日本の全企業」をどう作るか

三層に分けて考える。下の層ほど確実で、上の層ほど価値が高く不確実。

```
  第3層  人 (部署・役職・担当者)      ← 価値が高い / 取得が難しい
  ────────────────────────────────
  第2層  企業プロフィール + 動き
  ────────────────────────────────
  第1層  法人マスタ (骨格)            ← 確実 / 無料で全件取れる
```

### 3.1 第1層: 法人マスタ — 公的データで全件が取れる

| 出典 | 取れるもの | 費用 | 備考 |
|---|---|---|---|
| **国税庁 法人番号公表サイト** | 法人番号・商号・所在地・登記の変更履歴 | 無料 | **全件 CSV + Web-API + 日次差分**。約 500 万件超。これが唯一の SSOT |
| **gBizINFO** (経済産業省) | 業種・資本金・従業員数・法人サイト URL・許認可・調達実績・補助金・特許 | 無料 API | 法人番号で紐づく。**第2層への橋渡しとして極めて重要** |
| **EDINET** (金融庁) | 有価証券報告書の財務数値 (XBRL) | 無料 API | 上場・報告書提出企業のみ |
| **登記情報提供サービス** | 役員の氏名 | 1 件あたり数百円 | 全件は非現実的。**確度の高い相手にだけ使う** |

**ここは「全企業」を名乗れる唯一の土台**。無料で、日次で更新される。
まずこれを取り込むだけで、既に他社リストにない網羅性が出る。

注意: 法人番号は登記された法人すべてに振られるため、
**休眠・実体のない法人がかなり含まれる**。稼働判定 (サイトの有無、
直近の届出、求人の有無など) を別途スコア化する必要がある。

### 3.2 第2層: 企業プロフィール — 収集と紐付け

#### 最大の技術課題: 法人番号 ↔ 実在するサイト URL の紐付け

法人マスタ 500 万件には URL がない。ここを埋めるのが第一関門。

手順:

1. 商号 + 所在地で検索 → 候補 URL を複数取得
2. 候補サイトを取得し、**会社概要ページから所在地・電話・法人番号を抽出**
3. マスタと突き合わせてスコアリング
4. **確信度つきで確定** (100% は原理的に無理。確信度を持たせて運用する)

名寄せの難所:

- 表記ゆれ: `株式会社` / `(株)` / `㈱`、前株・後株、旧字体、全角半角
- 同名企業: 「株式会社サンプル」は全国に何十社もある → **住所と電話で切り分ける**
- 支店・営業所が独自サイトを持つ場合
- 持株会社と事業会社の関係

対策: 商号の正規化ルール + 住所のジオコーディング (国土地理院 API は無料) +
電話番号一致。**確信度が低いものは「未確定」として保持し、切り捨てない**。

#### サイトから抽出するもの

| ページ | 抽出内容 | 営業上の意味 |
|---|---|---|
| 会社概要 | 資本金・設立・従業員数・事業内容・役員・拠点 | 規模でのセグメント分け |
| 採用ページ | 募集職種・部署名・人数 | **成長シグナル + 組織図の推定** |
| ニュース / IR | 資金調達・新拠点・新製品・提携 | **「なぜ今」の理由になる。最重要** |
| サービス紹介 | 提供内容・顧客層 | 自社商材との相性 |
| 問い合わせページ | フォームの URL・入力欄の構造・営業お断り文言 | 接触経路の確定 |
| HTML / ヘッダ | 使用している技術 | IT 商材なら強力な手がかり |

抽出には LLM を使う。HTML を投げて、あらかじめ決めた項目に構造化させる。
正規表現で組むより、サイトごとの構造の違いに強い。

#### 「動き」の検知 — これが差別化の核心になる

静的な属性 (業種・規模) だけのリストは、既に安価に手に入る。
**価値が高いのは「今、動いている企業」**。

- 求人が出た → 部署が増える / 課題がある
- 資金調達した → 予算がある
- 新拠点を開設した → 設備・システムの需要
- 経営陣が交代した → 方針が変わる
- 許認可を取得した (gBizINFO) → 新事業を始める
- 補助金に採択された (gBizINFO) → **予算の使い道が確定している**

これらを日次で差分検知し、**「シグナルが立った企業」を配信する**。
リストを売るのではなく、**タイミングを配信する**。ここに寄せたい。

### 3.3 第3層: 人 — 「担当者まで全部わかる」の現実

率直に書く。**全企業の担当者を実名で網羅するのは、合法的な手段では不可能**。
その前提で、**解像度を階層化して、それぞれに合った打ち方をする**のが正解。

| 段階 | 内容 | 到達できる割合の目安 | 打ち方 |
|---|---|---|---|
| **A** | 実名 + 個人アドレス | 5〜15% | 個人宛メール。最も反応が良い |
| **B** | 実名 + 部署・役職 | 20〜35% | 代表窓口に「○○部 ○○様」と宛名を書く |
| **C** | 部署・役職のみ (推定) | 60〜80% | 「情報システム部門ご責任者様」宛 |
| **D** | 代表窓口のみ | 100% | フォーム送信 / `info@` 宛 |

**実務上、B と C で十分に戦える。** 「情報システム部門のご責任者様」宛の
フォーム送信は、社内で正しく転送されることが多い。
実名にこだわるより、**部署の特定精度を上げる方が費用対効果が高い**。

#### 合法的に人物情報が取れるところ

- コーポレートサイトの**役員一覧・組織図・部門紹介**
- **プレスリリース**の末尾 ——「本件に関するお問い合わせ: ○○部 ○○」
  ここは宝の山。部署名と担当者名がセットで公開されている
- **求人票**の「配属部署」「募集背景」→ 組織構造が読める
- 登記の役員情報 (有料・確実)
- 登壇者情報、技術ブログの著者、特許の発明者
- 入札・許認可情報の担当部署 (gBizINFO)

#### やらないこと (明確に線を引く)

- **ビジネス向け SNS のスクレイピング** — 利用規約違反。訴訟の実例がある
- **メールアドレスのパターン推測による総当たり送信** —
  届かないメールが増えると送信ドメインの評価が落ち、
  **正規のメールまで届かなくなる**。事業の自殺行為
- **CAPTCHA の突破**
- **非公開情報の購入**

## 4. 接触の実行基盤

### 4.1 メール送信 — 勝負は「到達性」で決まる

いくら良い文面でも、迷惑メール判定されたら 0 件。
**ここに一番時間をかける**。

構成:

- **送信専用ドメインを本体ドメインと分ける**
  (評価が落ちたときに本業のメールを巻き込まない)
- SPF / DKIM / DMARC を正しく設定
- **暖機運転**: いきなり大量に送らない。日次量を数週間かけて上げる
- 複数ドメイン × 複数メールボックスを回して、1 箱あたりの量を抑える
- 送信基盤は Amazon SES が費用面で有利 (審査あり)。
  到達性重視なら Postmark / SendGrid も候補
- **バウンスと苦情の即時処理**。
  SES はバウンス率 5%、苦情率 0.1% を超えると審査対象になる
- 配信停止リンクを全通に入れる (法定要件)

### 4.2 問い合わせフォーム自動送信

Playwright でブラウザを動かす。

1. フォームの URL を開き、入力欄の構造を解析
2. **入力欄のラベルと意味を LLM で対応づける**
   (「御社名」「会社名」「Company」→ 会社名、という揺れを吸収)
3. 送信前チェック:
   - CAPTCHA があるか → **あれば中止**
   - 「営業お断り」の文言があるか → **あれば中止**
   - 既にこの企業に送っていないか → **送っていれば中止**
4. 入力して送信、送信後の画面を保存 (成功の証跡として)
5. 結果を記録

成功率は 60〜80% 程度を見込む。残りは構造が特殊・CAPTCHA あり・
フォームがないなど。**失敗を正しく記録して、代替経路 (メール) に回す**。

### 4.3 接触の流れ (多段階)

```
  Day 0   フォーム送信 (最も届く)
    ↓ 反応なし
  Day 4   メール 1 通目 (シグナルに触れた内容)
    ↓ 反応なし
  Day 11  メール 2 通目 (角度を変える)
    ↓ 反応なし
  Day 21  メール 3 通目 (最後の連絡と明示)
    ↓
  終了 → 再接触は 6 ヶ月後まで禁止
```

開封・クリック・返信を検知したら**その時点で自動送信を止め、人に渡す**。
自動化の目的は「人が話すべき相手を見つけること」であって、
送り続けることではない。

### 4.4 文面の作り方

一律の文面は反応しない。かといって全件を手書きはできない。
**シグナルを差し込む半自動が現実解**。

```
  骨格 (人が作る) × シグナル (自動で挿入) × 部署 (自動で選択)
```

例:「先日の〈○○拠点開設〉の発表を拝見しました」の部分だけを
第2層で取ったシグナルから生成する。ここは LLM が効く。

## 5. システム構成 (案)

```
 ┌─ 収集層 ────────────────────────────────────────┐
 │  公的データ取込 (法人番号 / gBizINFO / EDINET)   │
 │  Web クローラ (robots.txt 遵守・レート制限)      │
 └───────────────────┬─────────────────────────────┘
                     ↓
 ┌─ 加工層 ────────────────────────────────────────┐
 │  正規化 → 名寄せ (確信度つき) → LLM 構造化抽出   │
 │  → シグナル差分検知 → 品質スコア付与             │
 └───────────────────┬─────────────────────────────┘
                     ↓
 ┌─ 蓄積層 ────────────────────────────────────────┐
 │  PostgreSQL (マスタ) / 全文検索 / 生 HTML 保管   │
 │  ベクトル検索 (「この会社に似た会社」用)         │
 └───────────────────┬─────────────────────────────┘
                     ↓
 ┌─ 実行層 ────────────────────────────────────────┐
 │  ★ 送信前ゲート (配信停止照合 / お断り検出 /     │
 │     重複排除 / CAPTCHA 検出) ← ここは必ず通す    │
 │  メール送信ワーカー / フォーム送信ワーカー       │
 │  反応の追跡 (開封・クリック・返信・バウンス)     │
 └───────────────────┬─────────────────────────────┘
                     ↓
 ┌─ 画面層 ────────────────────────────────────────┐
 │  条件検索・リスト作成 / 配信管理 / 反応の可視化  │
 │  CRM 連携 / 監査ログ閲覧                         │
 └─────────────────────────────────────────────────┘
```

**★ の送信前ゲートは、すべての送信が必ず通る単一の関門として実装する。**
経路ごとにチェックを書くと、いずれ抜ける。ここは構造で守る。

技術選定は `.ccagi.yml` に沿って TypeScript / Node.js を基本とし、
クローラとフォーム送信は Playwright。設計の詳細は Phase 2 で確定する。

## 6. 作る順番

**法務 → 土台 → 検索 → 送信** の順。逆にやると作り直しになる。

| 段階 | やること | 完了の目安 | 想定 |
|---|---|---|---|
| **0. 法務設計** | プライバシーポリシー・利用目的の公表・配信停止の窓口・社内基準の文書化 | 公開できる状態 | 2〜3 週 |
| **1. 法人マスタ** | 国税庁データ全件取込 + 日次差分 + gBizINFO 統合 | 500 万件が検索できる | 3〜4 週 |
| **2. URL 紐付け** | 商号・住所からサイトを特定、確信度つきで保存 | 主要企業の 7 割以上に URL | 4〜6 週 |
| **3. サイト収集** | クロール + LLM 構造化抽出 (業種・規模・窓口・お断り判定) | プロフィールが埋まる | 6〜8 週 |
| **4. 検索画面** | 条件でセグメントを作り、リストを確認できる | **ここで社内で使い始められる** | 3〜4 週 |
| **5. フォーム送信** | 送信前ゲート + Playwright ワーカー | 実送信と記録 | 4〜6 週 |
| **6. メール送信** | ドメイン整備 + 暖機運転 + 配信停止処理 | 到達率が安定 | 6〜8 週 (暖機に時間がかかる) |
| **7. シグナル** | 差分検知 → 「今動いている企業」の日次配信 | **ここが差別化の完成** | 4〜6 週 |
| **8. 人物解像度** | プレスリリース・求人からの部署抽出、必要な相手だけ登記照会 | 段階 B/C の割合を上げる | 継続 |

**段階 4 で一度止めて、自社で使う。**
外に出すのはそのあと。自分たちが使って効かないものは、売っても効かない。

## 7. 数字の見通し

### 反応率 (BtoB の一般的な水準)

| 経路 | 開封 | 反応 | 備考 |
|---|---|---|---|
| 一律のメール | 15〜25% | 0.3〜1% | 文面が汎用だとここまで落ちる |
| シグナル込みのメール | 25〜40% | 1〜3% | **差し込みの精度で倍以上変わる** |
| 問い合わせフォーム | — | 1〜3% | 担当者に転送されるため届きやすい |

1 万社に接触して 100〜300 件の反応、というのが現実的な目安。
**リストの量より、シグナルの鮮度で反応率が動く。**

### 費用の主な発生源

- クロール (通信・計算資源) — 全件を回すと重い。**優先度をつけて回す**
- LLM の抽出・生成 — 件数 × 単価。安いモデルで一次選別 → 高いモデルで精査、の二段構えで抑える
- メール送信 — SES なら安価。到達性の作り込みは人的コスト
- 登記情報 — 1 件数百円。**全件は不可。確度の高い相手だけ**

## 8. 競合と、どこで勝つか

| 領域 | 既存 | 特徴 |
|---|---|---|
| 企業リスト | Musubu / FUMA / ユーソナー | 網羅性はある。**静的な属性が中心** |
| フォーム営業 | GeAIne / APOLLO SALES / Sales Crowd | 送信の自動化に特化。**データは薄い** |
| 大手 | Salesforce 系 | 高機能・高価格。日本企業の網羅性は弱い |

**多くが「リストを作る側」と「送る側」に分かれている。**
両方を持ち、かつ **シグナルで繋ぐ**ところが空いている。

勝ち筋の候補 (どれか一つに絞る):

1. **タイミング特化** — 「動いた企業」を毎朝配信する。リストではなく機会を売る
2. **部署解像度** — 「誰に」の精度で差をつける。プレスリリース・求人の解析に投資
3. **法令遵守を売りにする** — 監査ログ・配信停止管理・お断り自動除外を標準装備。
   コンプライアンスに厳しい大企業が使える唯一の選択肢になる

個人的には **1 を軸に、3 を土台にする**のが良いと考える。
2 は 1 の精度を上げる手段として後から効いてくる。

## 9. 主なリスク

| リスク | 影響 | 対策 |
|---|---|---|
| 送信ドメインの評価失墜 | **事業が止まる** | 本体ドメインと分離。暖機運転。バウンス即処理 |
| 苦情・行政指導 | 事業停止 | 送信前ゲートの単一化。全件の監査ログ |
| フォーム送信への抗議 | 信用低下 | 1社1回。お断り検出。送信頻度の抑制 |
| 名寄せの誤り | 誤送信 = 信用低下 | 確信度で足切り。低確信は人が確認 |
| 収集先の構造変更 | データが古くなる | 抽出の異常を検知して警告 |
| 個人情報の開示請求対応 | 法令違反 | 段階 0 で窓口を用意。人物データの出所を必ず記録 |

## 10. 決まった方針 (2026-08-09)

| 論点 | 決定 | 効いてくるところ |
|---|---|---|
| 自社利用型か、リスト提供型か | **自社利用型** | 個人情報保護法の第三者提供にあたらない。オプトアウト届出が不要になり、負担が大幅に軽い (§2.2 の A) |
| 狙う相手 | **先に絞らない。全法人を持ち、必要なときに業種・業態で切り出す** | 基盤を「全件保持 + 絞り込み」として作る。特定の業種に最適化しない |
| 社内利用か外販か | **当面は社内利用のみ** | 画面や権限管理より、データの網羅性と絞り込みの精度を優先する |
| 作る順番 | **§6 の段取りどおり。段階 4 まで先に通す** | 送信より先に、切り出せる状態を作る |

### この決定から外れる設計

- リスト書き出しは社内向けの CSV に限る。外部提供の導線は作らない
- 担当者情報は「取得したら自社の営業に使う」だけ。渡さない・売らない
- 利用目的の公表 (法21条) は必要。プライバシーポリシーに明記する

### 実装の現在地

段階 1 (法人マスタ) は完了。581 万件を取り込み、閉鎖・除外を落とした
営業対象 500 万件を、地域・法人種別・法人格・設立時期・商号の語で
絞り込める状態まで到達している。使い方は [README](./README.md)。

**次の関門は業種**。国税庁のデータに業種は無いため、gBizINFO の
アクセストークン取得が段階 2 以降の前提になる。
