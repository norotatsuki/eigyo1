# 営業リスト基盤 — 使い方

日本の全法人を手元に持ち、条件で切り出して営業に使うための土台。
**社内利用のみ**。リストを外部に提供する運用は想定していない (理由は
[構想書](./sales-platform-concept.md) §2.2)。

## 現在できること

| できること | 状態 |
|---|---|
| 全法人 581 万件の取り込み (国税庁) | 動作 |
| 閉鎖・除外の除去 (営業対象 500 万件を判定) | 動作 |
| 地域 (都道府県・市区町村)・法人種別・法人格・設立時期での絞り込み | 動作 |
| 商号の部分一致検索 (全角半角のゆれを吸収) | 動作 |

## 必要なもの

- Node.js 22 以上
- `unzip` コマンド (macOS / Linux には標準で入っている)
- 空き容量 約 5GB (データベース 3.2GB + 生 zip 250MB)

## 準備

```bash
npm install
```

## 画面で使う（社内向け・おすすめ）

```bash
npm start
```

`http://127.0.0.1:5173/` を開く。使用中なら空いている口を自動で探し、
実際に開いた URL を表示する。

**127.0.0.1 のみ待受**なので、社外どころか同じ社内ネットワークの
他の端末からも届かない。公開 URL は無い。これは意図した設計で、
581 万社のデータと営業記録を外部に置かないため
（構想書 §2 / `.claude/rules/info-public-guard.md`）。

他の人にも使わせたい場合は、待受を `0.0.0.0` に変える必要がある。
そのときは社内網に限定するか、認証を付けること。既定では変えていない。

左の絞り込みで条件を積み、右の一覧で中身を見て、そのまま CSV に書き出す。
業種・都道府県・市区町村・法人種別の選択肢には**実件数**が出るので、
「選べるのに 0 件」が起きない。

都道府県を 1 つ選ぶと市区町村が出る (港区だけ、のように区単位で狙える)。
複数県を選んでいるときは同名の町が並んで選べないため出さない。

初回だけ選択肢の集計に 1 分ほどかかる（結果を控えるので 2 回目以降は一瞬）。

## 取り込み

```bash
# 全国 581 万件。約 5 分、zip 250MB のダウンロードを伴う
npm run cli -- ingest

# 小さく試したいとき
npm run cli -- ingest --region 鳥取県
```

国税庁のデータは毎月更新される。同じコマンドを流し直せば上書きされる
(法人番号を鍵にした更新なので、重複は増えない)。

## 業種を付ける

```bash
npm run cli -- classify
```

商号と法人格から業種 (日本標準産業分類) を推定して付加情報に書き込む。
500 万件で約 2 分。何度実行しても結果は変わらない。

```
確信度の分布 — 実際の営業に使うなら 0.7 以上を薦める
  1.0      20,406  確か
  0.9     307,907  確か
  0.8     235,053  確か
  0.7     182,718  確か
  0.6     134,534  手がかり程度 (「工業」「商事」など幅の広い語)
  0.5     340,860  手がかり程度
  → 0.7 以上は 746,357 件
```

規則は当てずっぽうで足していない。未分類の商号を数え、候補語ごとに
実物を見てから採否を決めている。却下した語 (ハウス / 工房 / ロジ /
地建 / スタッフ) は理由つきで `src/enrich/industry/rules.ts` に残してある
——「ハウス」はクレープハウスを、「ロジ」はプロジェクトを拾ってしまう。

**これは推定であって、権威ある出典ではない。** 実際に確かめた質は次のとおり。

| 確信度 | 判断の根拠になる語の例 | 実際の精度 |
|---|---|---|
| 0.9-1.0 | 歯科 / クリニック / 酒造 / 運送 / 医療法人 / 税理士法人 | ほぼ正しい |
| 0.7-0.8 | 建設 / 工務店 / 不動産 / 印刷 / 倉庫 / 介護 | おおむね正しい |
| 0.5-0.6 | 工業 / 商事 / 商会 / テック / 製作所 | **当てにならない**。幅が広すぎる |

営業に使うときは `--industry-confidence 0.7` を付ける。

gBizINFO のような公的な出典が入ったら、そちらが優先される
(`industry_source` が `gbizinfo` / `manual` の行は推定で上書きされない)。

## 接触先を自分で探す — サイトの発見と収集

**国税庁のデータに URL は無く、gBizINFO はトークンが要る。**
そこで実在する企業サイトの側から集めて、法人番号に突き合わせる。
出どころは **Common Crawl の公開索引**（無料・トークン不要）。

```bash
# 1. ホスト名を集める（*.co.jp。索引は 1,340 ページ、全体で約 34.8 万ホスト）
npm run cli -- discover --pages 50

# 2. 訪ねて接触先を取り出し、法人番号に突き合わせる
npm run cli -- crawl --limit 500

# 3. 突き合わせ方を改善したら、訪ね直さずに計算し直す
npm run cli -- rematch
```

**3 が要る理由**: 照合の改善のたびにサイトを訪ね直すのは相手に失礼で、
時間もかかる。取ってある会社名と住所は変わらないのだから手元で計算し直せば足りる。
実際、郵便番号照合を後から入れたときはこれで全件を上げ直した。

```
訪問 40 件
  取得できた              31
  接続できなかった         9
  法人番号に紐付いた      15
  問い合わせ先が判明      27
```

### 相手に迷惑をかけないための決まり

- **robots.txt に従う**。禁じられていれば訪ねない
- **1 サイト最大 3 ページ**（トップ / 会社概要 / 問い合わせ）
- **1.5 秒の間隔**を空ける
- 名乗る（`eigyo1-site-collector/0.1`）

### 突き合わせの確からしさ

| 方法 | 確信度 | 条件 |
|---|---|---|
| `name_postal` | 0.97 | 商号が一致し、**郵便番号**も一致 |
| `name_address` | 0.95 | 商号が一致し、住所の市区町村まで一致 |
| `name_pref` | 0.85 | 商号が一致し、都道府県が一致（その県に 1 社だけ） |
| `name_only` | 0.60 | 商号が全国で 1 社しかない |

郵便番号を最優先にしているのは、国税庁側の所在地が全角
（`東京都港区南青山２丁目２－１５`）でサイト側が半角
（`東京都港区南青山2-2-15`）という食い違いが常態だから。番号なら揺れない。

同名の会社は全国に何十社もある。**決められないときは紐付けない。**
誤った宛先を作るより、空欄のままの方がましである。

### 実データで見つけて直した欠陥

| 症状 | 原因 | 対処 |
|---|---|---|
| 「千歳烏山の不動産なら株式会社」を社名として拾う | 題名の宣伝文句ごと後株判定 | 前株を優先。後株は区切りがほぼ社名のときだけ |
| 「〒100-0001」から「00-0001」を電話番号に | 郵便番号の途中に一致 | 前後の数字を見て桁数を検める |
| 全角ハイフンの郵便番号を取り逃す | NFKC でも `−` (U+2212) は残る | 横棒をまとめて受ける |
| 収集のたびに次の画面起動が 40 秒待ちに | 集計の控えを捨てるだけだった | 収集の最後に作り直す |

## 送る — 設定を入れれば全自動

```bash
npm run cli -- init-config          # 設定のひな形を作る
npm run cli -- config               # 足りない項目を挙げる
```

`outreach.config.json` の `identity` 4 項目は**特定電子メール法 4 条の要求**で、
埋まるまでメールは送れない。認証情報だけは設定ファイルに書かず、
環境変数 `EIGYO_SMTP_PASS` から読む。

```bash
# 下見。誰に何が送られるかを先に見る (1 件も送らない)
npm run cli -- send --channel form --has-form --limit 50 \
  --campaign "2026夏" --template tpl.json

# 実際に送る
npm run cli -- send --channel form --has-form --limit 50 \
  --campaign "2026夏" --template tpl.json --live
```

文面のひな形 (`tpl.json`):

```json
{ "name": "夏の提案", "channel": "form",
  "subject": "業務効率化のご提案",
  "body": "{{会社名}} ご担当者様\n\n{{自社名}}でございます。..." }
```

使える差し込み: `会社名 / 法人番号 / 都道府県 / 市区町村 / 業種 / 宛名 /
自社名 / 自社住所 / 配信停止 / 問い合わせ先`

### Gmail で送る

```bash
npm run cli -- init-config --preset gmail
```

Gmail は SMTP で送れる。必要なのは**アプリパスワード**（二段階認証が前提）。

1. Google アカウントで二段階認証を有効にする
2. https://myaccount.google.com/apppasswords で発行する
3. `export EIGYO_SMTP_PASS="発行された16桁"`
4. `email.fromAddress` と `email.smtp.user` に Gmail のアドレスを入れる

**普段使いのアドレスから大量に送らないこと。** 無料 Gmail の上限は
1 日 500 通、Workspace は 2,000 通だが、それ以前に迷惑メール報告が続くと
**アカウント自体が止まる**。上限は既定で 100 通（Workspace は 300 通）に
してある。少量で反応を見てから増やすこと。

長く続けるなら、送信専用のドメインを取って本業のメールと分ける方がよい。

### 送らせない仕組み (5 段)

1. **設定** — 法定表示 4 項目と認証情報が欠けていたら実行しない
2. **文面** — メールは法定表示が本文に出ていなければ実行しない
3. **上限** — その日の送信数が上限に達していたら実行しない
4. **ゲート** — 除外 / お断り / 送付済み / 冷却 / 宛先なし を落とす
5. **差し込み** — 値が埋まらない先は外す。「{{業種}}の皆さま」が
   「の皆さま」になった文章を相手に送らない

さらに **`--live` を明示しない限り 1 通も送らない**。事故は「うっかり本番」で起きる。

### 問い合わせフォームの自動送信

欄の意味を見出しから推し量って埋める。**CAPTCHA を見つけたら必ず中止**
（突破は不正アクセス禁止法と業務妨害の領域。回避策は実装しない）。
意味を判じられない必須欄が残った場合も送らない。

送信ボタンを押しただけでは成功と呼ばない。相手側の入力チェックで
止まっていないか、画面が実際に変わったかを確かめてから「送信済み」にする。

```
=== 試験用フォーム 3 種に対する実測 ===
  候補 3 / 送信 1 / 見送り 2
    見送り: CAPTCHA を検出 (g-recaptcha) — 突破しない
    見送り: 意味を判じられない必須欄: ご契約番号
=== 同じ条件で 2 回目 ===
  送信 0 / ゲートで除外 1 — {"already_sent":1}
```

## LLM で取りこぼしを埋める

正規表現では「会社概要の表」のような決まった形しか拾えず、実測で
**会社名 68% / 住所 65%** が上限だった。文章に紛れた書き方は取れない。
そこを LLM に読ませて埋める。

```bash
npm run cli -- llm --limit 100 --classify --estimate   # 費用の見積もりだけ
npm run cli -- llm --limit 100 --classify              # 実行
```

鍵は環境変数 `OPENAI_API_KEY` から読む。設定ファイルには書かない。

**サイトは訪ね直さない。** 収集のときに本文を保存してあるので、
手元の文章を読ませるだけで足りる。相手に負担をかけない。

### 絶対にやらないこと — 接触先を LLM に作らせる

LLM は「株式会社山田建設のメールアドレス」を**知らない**。
聞けばもっともらしい答えを返すが、それは創作である。
存在しない宛先に送ればバウンスで送信元の評価が焼け、最悪は
**無関係な第三者に届く**。

そこで **LLM の出力は原文と照合してから採用する**。

```
LLM の答え:  info@sample-kensetsu.com
原文:        info@sample-kensetsu.co.jp
             → 原文に無いので捨てる
```

照合は表記のゆれを吸収する（原文が全角、応答が半角は日常的に起きる）。
形の検めも通す（メールアドレスの形をしていない値は採らない）。
業種は判断の結果なので原文に現れない。代わりに、返せるコードを
日本標準産業分類の一覧に限り、一覧に無い番号は捨てる。

| 用途 | 検証の方法 |
|---|---|
| 会社名・住所・電話・メール | **原文に含まれること**を確かめる |
| 業種 | 日本標準産業分類の一覧にあるコードだけ + 確信度を保存 |
| 接触先の生成 | **やらない** |

出典は `industry_source = llm_classify` として残るので、あとから
選別も取り消しもできる。

### 費用 — まず無料で済ませ、残りだけ払う

**順序が大事。** いきなり LLM にかけると無駄に払うことになる。

```bash
# 1. まず無料。本文のキーワードで業種を当てる
npm run cli -- classify

# 2. 残りだけ、しかも送る範囲に絞って
npm run cli -- llm --pref 13 --industry 39 --classify --estimate
```

| 対象 | 費用 (gpt-4o-mini) |
|---|---|
| 全 348,000 件 / 抽出のみ | $61 |
| 全 348,000 件 / 抽出＋分類 | $123 |
| 東京都の IT 11,000 件 | $3.88 |
| **1 回の施策 1,000 件** | **$0.35** |

**全件にかける必要はまず無い。** 実際に要るのは、これから接触する範囲だけ。
`--pref` `--industry` などの絞り込みを付けると、その範囲だけを補完する。

見積もりは推測ではなく、保存済みの本文を実際に抜粋して長さを測って出す。
`--estimate` を付けると見積もりだけ出して終わる。

#### 費用を下げている 3 つの仕掛け

1. **無料の分類を先に通す** — 業種は商号だけだと 20% しか当たらないが、
   本文にも同じ規則をかけると 80%。LLM が要るのは残りだけ
2. **本文を抜粋して送る** — 会社情報は「会社概要」「〒」「TEL」の近くに
   固まっている。その周辺だけにして実測 2,307 文字 → 861 文字 (37%)
3. **範囲を絞る** — 全件ではなく、これから送る先だけ

### 本文からの業種分類 — 出現回数で重み付けする

素朴に「最初に見つかった語」を採ると外す。実測した誤り:

| 会社 | 素朴な判定 | 出現回数で重み付け |
|---|---|---|
| 廿日市交通 | 道路貨物運送業（運送 ×1） | **道路旅客運送業**（タクシー ×6） |
| 株式会社LIBRA | その他の製造業（製造 ×1） | **判定を見送り** |
| 21インコーポレーション | 銀行業（支払い案内の「銀行」） | 映像制作業（映像 ×5） |

本当に建設会社なら「建設」は何度も出る。取引先として 1 回名前が挙がる
だけとは違う。3 回未満の語は、たまたま出ただけとみなして採らない。

**精度の数字は出していない。** 標本 25 件では統計的に何も言えないため。
個別の誤りが直ったことは確認したが、「何%正しい」は収集が進んでから測る。

## 送る前に必ず通すもの — 送信前ゲート

**すべての接触はゲートを通す。** 経路ごとに判定を書くと、いずれ必ずどこかが
抜ける。抜けた先で起きるのは「断られた相手への再送」であり、
特定電子メール法 3条3項の違反にあたる。

```bash
# 1. 条件に名前を付けて残す
npm run cli -- segment --save "東京のIT" --pref 13 --industry 39 --industry-confidence 0.7

# 2. 送れるかを判定する（まだ送らない）
npm run cli -- outreach --use "東京のIT" --check postal --campaign "2026夏DM"

# 3. 送ったら記録する
npm run cli -- outreach --use "東京のIT" --record postal --campaign "2026夏DM"

# 4. もう一度流しても、同じ先には送らない
npm run cli -- outreach --use "東京のIT" --check postal
#   → 送れる: 0 件 / 止めた: N 件（理由 cooling）
```

ゲートの判定順は **除外 → お断り → 送付済み → 冷却 → 宛先** で固定。
止めた判断も記録に残す。残さないと「なぜこの会社に送っていないのか」を
後から説明できない。

| 経路 | 上限 | 冷却期間 | 必要な宛先 |
|---|---|---|---|
| postal 郵送 | — | 90 日 | 所在地（全社にある） |
| email メール | — | 30 日 | メールアドレス |
| form 問い合わせフォーム | **1 社 1 回** | — | フォームの URL |
| phone 電話 | — | 30 日 | 電話番号 |

フォームを 1 社 1 回に限っているのは、特定電子メール法の対象外である代わりに
反復送信が業務妨害にあたるという指摘があるため（構想書 §2.3）。
緩めるなら `src/outreach/gate.ts` を変える前に法務の確認を取ること。

## 除外リスト

```bash
npm run cli -- suppress --add 1234567890123 --reason opt_out --note "受信拒否の連絡"
npm run cli -- suppress                      # 内訳を見る
npm run cli -- suppress --remove 1234567890123
```

理由は `opt_out`（受信拒否）/ `refused`（サイトにお断り表示）/ `customer`（取引先）/
`competitor` / `bounced` / `manual` から選ぶ。

**積んだ先は検索からも消える。** リストに出てこなければ、間違って送ることもない。

## 業種の精度を上げるには

**業種は国税庁のデータに含まれていない。** 今入っているのは商号からの推定で、
確信度 0.7 以上でも 75 万件 (営業対象の 15%) にとどまる。
未分類 388 万件の大半は屋号 (コーポレーション / プランニング等) で、
商号から業種を読み取ること自体に天井がある。

権威ある出典として第一候補は gBizINFO (経済産業省)。法人番号を鍵に、
業種・資本金・従業員数・法人サイト URL が取れる。利用には無料の
利用者登録とアクセストークンが必要。

- 申請先: https://info.gbiz.go.jp/
- 一括ダウンロードと API の両方が提供されている
- **トークンを取得したら教えてください。取り込みを実装します**

取り込みが入ると、推定より gBizINFO が優先される作りになっている
(`industry_source` で出典を判別している)。

## 設計上の約束

### 営業対象の判定

法人番号は登記された全法人に振られるため、清算結了や合併で消えた法人が
80 万件以上含まれる。以下の 3 条件を満たすものだけを営業対象とする。

- 検索対象除外 = 0 (国税庁が公表対象から外していない)
- 登記記録の閉鎖等年月日が空 (清算結了・合併消滅などをしていない)
- 最新履歴等 = 1 (過去の履歴行ではない)

`--include-inactive` を付けると、この判定を外して全件を見られる。

### 営業お断りの尊重

`company_profiles.solicitation_refused` が 1 の先は、検索・書き出しから
既定で外れる。この列は今後のサイト収集で埋める。外すには
`--include-refused` を明示的に付ける必要がある。

### 商号の正規化を 2 つに分けている理由

- `name` … 国税庁の正式表記。表示・郵送に使う。**加工しない**
- `name_normalized` … 全角半角のゆれだけを吸収した形。検索の索引はこちら
- `name_core` … 法人格・記号・空白を落として詰めた形。名寄せの照合キー

所在地も同じ考えで、正式表記のまま保持している。

## データの置き場所

```
data/
├── eigyo.db          # SQLite。3.2GB
└── raw/              # 国税庁から取得した zip
```

`data/` は git の管理外。公的データなので、消しても取り込み直せる。

データベースの位置は環境変数 `EIGYO_DB` か `--db` で変えられる。

### なぜ SQLite か

社内利用で、まず動かすことを優先したため。サーバの用意が要らない。
複数人が同時に書き込む段階になったら PostgreSQL に移す。
読み取りだけなら SQLite のままで複数人が使える。

### 検索の速さについて（実測）

| 条件 | 一覧 | 件数 |
|---|---|---|
| 条件なし（500 万件） | 13 ms | 1.5 秒 |
| 東京都のみ（115 万件） | 8 ms | 0.13 秒 |
| 東京都 × 株式会社（68 万件） | 9 ms | 0.11 秒 |
| 東京都 港区（14 万件） | 14 ms | 0.2 秒 |
| 語「クラウド」× 情報サービス業 | 10 ms | 0.10 秒 |
| 東京都 × 情報サービス業 | 1.5 秒 | 3.5 秒 |

一覧と件数は別々に取りに行く。件数の集計は数秒かかることがあるため、
先に一覧を描いて件数を後から追いつかせている。

速さのために 3 つの仕掛けが入っている。壊すと一気に遅くなる。

1. **全文検索は必ず駆動側にする**（`CROSS JOIN`）。SQLite に任せると
   500 万行それぞれに全文照合をかける計画を立て、1 件の検索に 64 秒かかる
2. **取り込みと業種推定のあとに `ANALYZE`**。統計が無いと都道府県で
   絞った検索が全走査に落ちる（13 秒 → 1 秒台）
3. **件数は「全体 − お断り」の引き算**。500 万行それぞれに
   お断り判定を問い合わせると 7.2 秒、引き算なら 0.6 秒
4. **一覧で使う索引を `INDEXED BY` で固定**。索引を足すたびに最適化器の
   選択が揺れ、同じ一覧が 0 秒になったり 2.9 秒になったりした。
   ただし業種で絞るときは付加情報の側の方が選択的なので指定しない
5. **業種の前方一致は範囲比較**。`LIKE '39%'` は索引を使えない
