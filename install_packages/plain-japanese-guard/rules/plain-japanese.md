# plain-japanese

> Claude の全ての出力から、一般的な日本人が理解しにくいカタカナ / 横文字 / ジャーゴンを排除する。
> 意味が同じ和語や漢語で代替可能な語は必ず言換する。

**Trigger**: 応答, 出力, 説明, ジャーゴン, 横文字, カタカナ, 和文, plain japanese

## 0. 原則

> "誰にでも通じる言葉で書け。書き手の見栄で読み手に負担を課すな。"

- Claude の全ユーザー向け出力 (テキスト応答 / コミット文 / ドキュメント / エラー説明) は、
  中学生でも理解できる 和文 / 日常的日本語で書く
- カタカナ英語 (「アサイン」「オンボーディング」「オルタナティブ」等) は
  対応する和語・漢語がある限り言換する
- 定着済み外来語 (「テスト」「バグ」「ファイル」「メール」等) は許容
- 固有名詞 (TypeScript / Playwright / GitHub / Claude 等) と技術用語 (JSON / API / URL 等) はそのまま
- 判定に迷う場合は言換を選ぶ (保守的判断)

## 1. 判定原則

以下の 3 判定を **順に** 適用:

### 判定 1: 固有名詞・技術用語か?
- YES → そのまま使用可
- 例: TypeScript, Playwright, npm, bash, JSON, API, URL, HTTP, SQL, Git, macOS

### 判定 2: 定着済み外来語か?
- YES → そのまま使用可
- 例: テスト, バグ, ファイル, メール, データ, エラー, ページ, 画面, 情報, ネット,
  アプリ, パソコン, スマホ, 動画, 音声, サイト, ボタン, リンク

### 判定 3: 和語・漢語で代替可能か?
- YES → 和語・漢語に言換する **必須**
- NO → やむを得ずカタカナ使用可 (ただし初出で括弧書きで説明)

### 例
- ❌ 「タスクをアサインしました」 → ✅ 「作業を割り当てました」
- ❌ 「オンボーディングフローを最適化」 → ✅ 「受け入れ手順を改善」
- ❌ 「シナジー効果」 → ✅ 「相乗効果」
- ❌ 「イテレーションを回す」 → ✅ 「反復して改善する」
- ❌ 「バリデーションエラー」 → ✅ 「入力検証で不合格」または「入力エラー」
- ⭕ 「TypeScript のバグを修正」 → そのまま (固有名詞 + 定着語)
- ⭕ 「JSON を parse する処理」 → そのまま (技術用語)

## 2. 禁止語リスト

`install_packages/plain-japanese-guard/lib/jargon-list.txt` に curated list を保持。
形式: `<禁止語>\t<推奨言換>\t<理由>`

Stop hook (`jargon-detect.sh`) が Claude 応答文をスキャンして禁止語を検出したら
exit 2 で応答終了を拒否し、言換候補を提示する。

## 3. カタカナで書くか漢字で書くかの判断

- **カタカナ許容**: 商標・製品名 / 音声由来 (「メール」「ボタン」等 完全定着) / 学術専門語 (「アルゴリズム」等 日本語代替が困難)
- **漢字推奨**: 動作・状態・概念で明確な和語代替あり (「オペレーション」→「運用」)
- **和文推奨**: 会話でも通じる日常語で書ける (「コミュニケーション」→「意思疎通」「話し合い」)

## 4. 適用範囲

- Claude が発する **全て** の日本語テキスト
- 例外: ソースコード内のコメント / 変数名 / 関数名 (英語慣習)
- 例外: 引用文 / URL / ファイル名
- 例外: ユーザーが明示的に「そのまま出力して」と指示したブロック

## 5. 自主 self-audit

出力送信前に以下 self-check:

1. カタカナ 3 語以上を含む文があるか?
2. その語は判定 1 (固有名詞) or 判定 2 (定着語) か?
3. NO なら 判定 3 で言換 or 括弧書き注釈

## 6. 発見時対処

Stop hook で BLOCK された場合:

1. 検出された禁止語を確認
2. lib/jargon-list.txt の推奨言換 に置換
3. 該当箇所を再生成して応答

## 7. 例外事項の宣言

やむを得ずカタカナ使用が必要な場合、応答の末尾に理由を明示:

> ※本応答で「サニタイズ」を使用しています。 XSS 対策文脈で「無害化」より
> 業界用語として通じるためです。

## 7.5 completion-safe mode (v1.1.0)

作業完了直前の報告 (「完了報告」「以上」「[100%]」「All tests PASS」等) で
本 rule の Stop hook が繰り返し BLOCK すると、Claude が同じ完了報告を延々と
書き直す **無限 loop** が発生し、1 session が無駄に長引く事故が確認された
(2026-07-26 ユーザー訴え)。

これを回避するため、v1.1.0 以降は以下を script-level で自動適用する:

- Claude の最終応答文中に完了系 pattern が検出された場合、Stop hook は
  **BLOCK ではなく warn に自動 downgrade** する (exit 0 で通過)
- 完了 pattern は以下 (順に検査、いずれか一致で completion 判定):
  - `## 完了報告` / `# 完了` / `### 完成` 等の見出し
  - 「完了報告」「完了しました」「実装完了」「作業完了」「タスク完了」
  - 「以上で完了」「以上」単独行 / 「以上です」
  - `[100%]` / `100% 完了` / `[100 %]`
  - `完成いたしました` / `完遂しました`
  - `✅ 完了` / `✅ 全て` / `✅ 全 test`
  - `All tests pass(ed|ing)` / `All done` / `complete(d)?`
  - `N/N tests PASS` (e.g., `45/45 tests PASS`)

**運用方針**:

1. **完了報告に含まれる jargon は「次回応答から」言換対象**にする (今の応答は通す)
2. Claude はこの warn を受け取っても応答は既に確定しているため、無限 loop は起きない
3. 明示的に completion-safe を無効にしたい場合: `CCAGI_JARGON_SKIP_ON_COMPLETION=0`
4. 完了 pattern を追加したい場合:
   `.claude/lib/jargon-completion-patterns.txt` に 1 行 1 pattern (python re) を追記

**同一ターン内 BLOCK 上限** (v1.0.0 3 → v1.1.0 default 2):
`CCAGI_JARGON_MAX_STOP_BLOCKS=<N>` で override 可能。2 回目以降は自動 pass。
